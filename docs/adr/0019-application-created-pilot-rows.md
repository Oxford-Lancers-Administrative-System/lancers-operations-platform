# 19. Pilot rows the application creates carry a sentinel-only ownership marker

Date: 2026-08-12

## Status

Proposed — Brian's decision. LAN-76 is the first scenario that needs it, and the
pull request that adds this record is where the decision is taken.

Extends [ADR 0016](0016-controlled-production-pilot-data.md), which is otherwise
unchanged.

## Context

ADR 0016 and `docs/pilot-data-runbook.md` require every pilot-scenario row to
carry two ownership marks: a **deterministic primary key** from a block reserved
for the issue, and a **`PILOT-<ISSUE-ID>` sentinel** in a text column. Cleanup
deletes by the key, qualified by the sentinel. Both halves are required because
the key can never match a row the script did not create, and the sentinel
catches a key block copied carelessly from another scenario.

That works when the scenario's setup script creates the rows. From LAN-76
onward, most of them do not.

LAN-76's feature is event drafting in the operator shell, and its hosted test is
a human signing in to the deployed application and creating events through it.
The identifier is generated by PostgreSQL at insert time, so there is no
deterministic key for cleanup to use. The alternatives were both worse:

- **Have setup create the events instead.** Then the hosted test exercises rows
  a script arranged rather than rows the application produced, which is the one
  thing testing against hosted exists to avoid. It also writes club data into
  production that no feature reads. LAN-76's own locked production-handoff
  section rules it out: "The assertion-only setup must not manufacture club data
  unnecessarily."
- **Ship no cleanup.** Then every hosted feature test is permanent, and the
  cutover inherits an unbounded pile of synthetic events.

The remaining option is a cleanup keyed on the sentinel — which LAN-76's locked
handoff section names explicitly: "`cleanup.sql` for events created with the
required `PILOT-LAN-76` sentinel". This record generalises that one instruction
into a rule, because every remaining slice ticket is tested the same way.

## Decision

A pilot scenario whose rows are created by the **application** may delete by the
sentinel without a deterministic key, under three conditions, all machine-checked
by `tests/pilot-data-contract.test.ts`:

1. **The scenario declares it.** Its `README.md` carries the exact heading
   `## Ownership marker: sentinel only`, so anyone reading the scenario sees
   which shape it uses before they run anything.
2. **The predicate is pinned, not described.** The scenario, the table it may
   delete from, and the exact conjuncts of its `where` clause are listed in
   `SENTINEL_ONLY_DELETES` in that test. Adding or loosening one is a line in a
   diff.
3. **The sentinel is one of those conjuncts**, and the others narrow which of
   the sentinel's rows may go — for LAN-76,
   `status in ('draft', 'pending_approval', 'withdrawn')`, so an event that
   reached approval, and therefore carries invitations, responses or attendance,
   can never be deleted by it.

**Adding a scenario to that list is Brian's decision.** It is a relaxation of an
ownership rule for deletions against the one production database, and it is
taken in the pull request that adds the scenario, not by a lead in passing.

Everything else in ADR 0016 and the runbook is unchanged: transactional scripts,
a visible preflight, guards that raise rather than warn, refusal rather than
widening where a foreign key would cascade or null, and a durable pilot
foundation that no cleanup touches.

## Why the pinned list rather than a rule the test recognises

The first implementation of this was a rule: "the sentinel, plus at least one
further conjunct narrowing which rows may go". Independent review got through it
twice — LAN-76's status restriction could be replaced with `created_at is not
null` and the test stayed green, and a new scenario could delete from
`public.people` by sentinel and `id is not null`.

Both got through for the same reason: an assertion matching text cannot tell a
narrowing predicate from a vacuous one. So the predicate itself became the
contract, in the shape the worked example already used for its own deletes.
A test that recognises a _pattern_ is a test somebody will satisfy accidentally;
a test that pins the _value_ has to be edited on purpose.

## Consequences

**Good.** Hosted feature tests exercise rows the application really produced.
Each relaxation is visible in three places — the scenario README, the pinned
list, and this record. A future scenario cannot inherit the relaxation by
copying a directory, because the list will not have its name in it.

**Bad.** The marker is genuinely weaker than a deterministic key: `name like
'%PILOT-LAN-76%'` is a substring match on a column an operator types into, so
an event a human names carelessly could match. The status restriction bounds
what that costs — the worst case is deleting a draft that distributes nothing
and whose audit history survives — but it does not eliminate it. The runbook
says so in those words rather than claiming equivalence.

**Also bad.** There are now two ownership shapes to hold in mind, and a scenario
author has to know which one applies before writing a cleanup. The runbook's
§ The ownership marker is where that is decided, and the contract test refuses a
scenario that picks the second without saying so.

## Alternatives considered

- **A deterministic identifier the operator types into the event name**, so
  cleanup could key on it. It puts a UUID in front of a human, in a field the
  club will read, to satisfy a convention rather than a need.
- **A column recording that a row is pilot data.** Explicitly forbidden by the
  runbook and by ADR 0016: the marker is a naming convention, never a schema
  concept, and adding one is a domain-model change.
- **Deleting by `created_at` window.** Ownership by timing is not ownership; a
  concurrent write by anyone else lands in the same window.

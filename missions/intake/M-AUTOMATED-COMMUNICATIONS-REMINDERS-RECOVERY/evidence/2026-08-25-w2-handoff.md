## W2 — owner direction already given

Brian rejected the first W2 draft's plain signed-link journey and directed the
following revised product behavior. These directions are captured in the current
specification and mockup, but W2 still needs artifact-level review and approval.

1. WhatsApp should look and behave like a real approved WhatsApp template, not a
   page containing a raw link. It presents clear **Yes** and **No** actions.
2. Selecting **Yes** opens the club's event page and records Yes as the standing
   RSVP. Selecting **No** opens the No-specific page and records No as the
   standing RSVP. The click is the confirmation; the user is not left
   unanswered merely because follow-up work remains.
3. A No click initially records the honest default **No reason given**. That is
   the standing state until the player supplies the actual reason. The page must
   strongly explain why the club needs a reason and should prominently encourage
   changing to Yes, without pretending the default was player-supplied.
4. A Yes is already complete even when event-specific questions remain. Those
   questions are separately and clearly marked **Additional questions
   outstanding**. The player may change Yes to No, but that control should be
   visually secondary and lightly framed.
5. Both landing paths show the full event details and the player's current
   answer.
6. The page prominently tells the player about other outstanding invitations.
   The inbox distinguishes **New invitations**, invitations that still need an
   answer, and follow-up work such as missing reasons or event questions. The
   next invitation should be visually obvious.
7. Messages and pages may use accurate aggregate social proof such as **12 other
   members have RSVP'd Yes**. They must not reveal names or individual answers,
   fabricate counts, or use misleading pressure.
8. WhatsApp message 1, WhatsApp message 2, and email use distinct,
   progressively stronger copy. They should not merely resend the same message.
   The exact wording/template render still needs Brian's review.
9. Either authoritative answer stops later player-facing chase jobs. Missing
   questions or a missing No reason remain visible follow-up work, not an
   unanswered RSVP.
10. Direct free-text WhatsApp replies remain non-authoritative for Release One.

## W2 — unresolved before approval

The next agent must not silently resolve these points:

- **Spec and mockup approval:** Brian has not yet approved the revised W2 spec or
  mockup. The current HTML is a draft prepared for review.
- **WhatsApp button mechanics:** Meta separates Quick Reply webhook actions from
  Visit Website URL actions. A normal URL visit can be triggered by link previews
  or security scanners. The requested one-tap answer-plus-open-page behavior is
  acceptable only if implementation can prove previews/scanners cannot create a
  false RSVP. Otherwise the safe fallback is a Quick Reply that records the
  answer followed by a separate page link, visibly a two-tap journey. This
  constraint must be explained during review rather than hidden.
- **Aggregate peer visibility:** showing live Yes counts is a deliberate change
  from the prior zero-peer-visibility rule. Brian directed it, but approval of
  the revised W2 is what accepts the complete boundary and rendering.
- **Exact pressure copy and approved templates:** the content progression is
  directed; the exact language and true WhatsApp rendering still need visual
  approval and eventual Meta template approval.
- **No-page wording:** preserve the substantive rule — the click already records
  No with **No reason given**, while the page strongly asks for a real reason.
  Avoid wording that incorrectly says the No itself is not recorded until a
  reason is supplied.

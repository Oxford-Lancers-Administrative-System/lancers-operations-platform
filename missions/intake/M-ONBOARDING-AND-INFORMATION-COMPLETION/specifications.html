W1 — Bring last season's squad in

Nothing here is approved. This is a draft for you to correct. Five decisions below are genuinely open and are the reason this page exists; the rest follows from what you already settled on 2026-09-01.

In one paragraph

You have the squad in a spreadsheet. You open the roster board, pick Add players → Import, and drop the file in. Before anything is written you get a page listing every line of the file with what it will do — New, Carried forward, Unchanged, or Refused with the reason in words — and underneath it a possible duplicates section: anyone whose name or number matches somebody already on record, shown beside the candidate, waiting for you to say same person or different person. You confirm once. Everybody lands on the roster at onboarding with a full checklist, and their welcome goes into the queue.

The five decisions I need from you

1 · What columns does the file carry?

Recommended: first name, last name and mobile required; personal email, college and matriculation year optional. Nothing else.

Those three required are the required set at every tier in person-required.ts, and they are what a welcome needs in order to arrive. The three optional are things a club spreadsheet genuinely holds and that save the player retyping. Everything else onboarding asks for — date of birth, emergency contact, degree field, expected graduation — comes from nowhere on main, is asked of everyone anyway, and putting it in a file on somebody's laptop is a worse outcome than typing it once.

2 · Can the file overwrite a person the club already holds?

Recommended: no. A carried-forward person's own facts are never overwritten by the file. A difference becomes something the player confirms on the form.

The mission's standing rule — nothing a person says silently overwrites a value a human confirmed — reads the same way pointed at a spreadsheet. Last-file-wins is precisely the failure the whole provenance design exists to prevent.

3 · What does an unanswered duplicate do?

Recommended: it refuses its own row and nothing else. The other rows still apply.

The alternatives are both worse. Blocking the whole import means one ambiguous name holds up fifty people. Defaulting to create silently mints a second record of a real human. Refusing one row is visible, recoverable, and costs one more pass.

4 · Does confirming send the welcomes, or queue them?

Recommended: queue. You are told "42 welcomes queued", not "sent".

The invariant that nothing is ever sent by hand, and this mission rides Mission 4's scheduler verbatim (PR7-rides-m4). W1 enqueues onboarding-opened per new membership and stops there.

5 · Who is allowed to run it?

Recommended: four-role — President, Secretary, GM, Treasurer — not the general-operator floor the surrounding roster surfaces use.

This is the largest single write of personal data the application offers: it creates dozens of people who have not yet heard from the club. Every other consequential write in the application narrows.

Two things I did not decide. Column names, header order, the size limit and the template wording are delegated to the Mission Lead — mechanical, with the event import's own constants as precedent. And the season question stays where you put it: the import inherits the roster's current season and never creates one, so a local walk needs a seeded season until Mission 11 exists.

Current main grounding

The analogue is /operate/events/import — the club's only import, built by LAN-155 for Mission 2's W3. It is the analogue in full: the same three-state screen, the same proposal-before-write contract, the same confirmation table, the same partial-apply behaviour. You settled on 2026-09-01 that the roster import follows it rather than inventing a shape.

  • Three states of one screen — choose a file, read the proposal, confirm — held in one client component with one server action carrying an intent, exactly as import-screen.tsx and actions.ts do. Not three routes: a person staging table would be a record of people the club never agreed to hold.
  • The proposal travels in the form and is never stored. The file's text goes back to the browser and returns with the confirmation; the plan is rebuilt inside the apply transaction and refused unless the digest still matches. Abandoning leaves nothing behind because there was never anything to leave.
  • The outcome vocabulary and its colours — OUTCOME_LABELS and outcomeColour, with colour never the only carrier and every chip stating its outcome in words.
  • The em dash for an empty cell, and the highlighted cell as the statement of change — both settled with you on 2026-08-21.
  • The duplicate question is Mission 5's, already shipped. person-duplicate.ts answers "who might this already be" across first name, last name, aliases, every email and every phone, and never offers a merged-away record. This workflow calls it; it does not write a fourth implementation of the question.
  • The person write is Mission 5's too. enterReturningPlayer already mints a person, their contact points and a season membership.

The one departure, and it is why this workflow exists. The event import has no duplicate section, because two events with the same name on the same day are a refusal. Two people with the same name are a question, always. The confirmation therefore grows a section the event import has no need of.

What the operator does

  1. Opens the import from the roster board's Add players menu. The screen states the season it will write into, by name, before a file is chosen.
  2. Downloads the template — a header row for the agreed columns.
  3. Chooses a file. Refused whole, before any row is read, if it is over the size limit or its header is not one this importer recognises.
  4. Reads the proposal. One table, one row per line, each carrying its outcome. Underneath, the possible-duplicates section, each needing an answer.
  5. Confirms. One action. Everything that can apply applies; refused rows are reported and change nothing.
  6. Reads what happened. Counts by outcome, the names that arrived, the rows that did not and why, and how many welcomes were queued.
  7. Or abandons, at any point before confirming. Nothing is written.

What each row does

Outcome What it means What is written
New Nobody on record is this person. A person, their contact points, a season membership at onboarding, a full checklist from this season's item types, a welcome queued.
Carried forward A person on record, with no membership this season. A season membership at onboarding, a full checklist, a welcome queued. The person's own facts are not touched — decision 2.
Unchanged Already on this season's roster. Nothing. No second checklist, no second welcome.
Refused The row cannot be read as a person, or an unanswered duplicate blocks it. Nothing.

Membership status on arrival is onboarding for every row that writes one. Nothing else in the ladder is reachable from here: activation is W10.

When it goes wrong

What goes wrong What the operator sees
No file chosen One sentence, the shipped NO_FILE_CHOSEN_MESSAGE pattern.
File too large Refused whole before any row is read, with the limit stated.
Header not recognised Refused whole, naming the columns it expected.
A row is missing a required column That row is Refused with the missing field named. The rest still apply.
A row's mobile is unreadable Refused — a welcome that cannot be delivered is a person who never hears from the club.
Two rows in the file are the same person The second is Refused, naming the first line. The first is a usable person; the second adds nothing.
A possible duplicate is unanswered The row is Refused and the confirmation says so. Answer it and confirm again.
The roster moved between proposal and confirm The apply refuses whole, on the shipped digest rule, and a fresh proposal is read.
The operator abandons Nothing is written, anywhere. The file was never stored.
The apply fails partway One transaction. Either the whole apply committed or none of it did.
No season exists The screen is unavailable, with the reason, and the operator is sent to make a season — which is Mission 11's.

Safety, privacy and authority

  • This is the largest single write of personal data the application offers. It is therefore four-role, and the guard is enforced twice — at the page and again in the service — as /operate/events/import does.
  • The file is never stored. It exists as form text between the proposal and the confirmation and nowhere else. No staging table, because a staging table is a record of people the club has not decided to hold.
  • The welcome is the one message the club may send without consent, and its purpose is to obtain it. W1 queues it and nothing else. No other message reaches an imported person until they tick.
  • No date of birth in an import. DOB is restricted, never appears on a list, board or queue, and is asked of the player at onboarding. A column for it here would put it in a spreadsheet on somebody's laptop.
  • Every arrival is audited — who imported, when, from which file name, and which rows. The append-only audit substrate is shipped.
  • Nothing gates. An imported player is a full member of the squad from the moment they land, invitable to events, with an empty checklist behind them.

How it gets proved

  • A walk on a fresh local stack with a seeded season: a file of ~50 synthetic players imports, the proposal names each outcome correctly, one deliberate duplicate appears in its section and blocks its row until answered, one malformed row is refused while the rest apply, and the board afterwards holds exactly the expected squad at onboarding with full checklists.
  • The same file imported twice: the second run is every row Unchanged, no second checklist and no second welcome.
  • Abandoning at the proposal writes nothing — proven by the roster being unchanged and no staging row existing to find.
  • A non-four-role operator is refused at the page and at the service.
  • Welcomes appear as queued dispatches, not as sends.
  • Desktop and 375px screens for the three states, both sides.
  • grounding: application-walked.
